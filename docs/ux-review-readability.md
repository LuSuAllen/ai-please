# AI, PLEASE · 可读性与认知负荷评审

评审对象：像素风手机竖屏《AI, PLEASE》DAY 01 全流程
素材：docs/shots/01–08（390×844 主视口、320×568 窄屏、1280 桌面）+ src/screens、src/components、src/data、src/styles
约束：不改玩法规则与数据（engine.ts / rules.ts / visitors.ts / regions.ts 的数值与判定逻辑不动），只改呈现与引导；主要操作常驻可达
日期：2026-10-24

---

## 0. 结论

**整体：视觉语言成立，信息架构不成立。**

- 像素终端美学（硬边框、扫描线、单色荧光、mono 数字）在 8 张图里高度一致，可读性的问题不在风格，在**层级**。
- 第一位的可理解性不达标：局内没有任何一句任务陈述，规则入口在滚动区最底部，8 个字段与 5 条规则之间没有一条显式连线。玩家要么先背规则，要么靠猜。第一访客结束后，反馈只告诉他「对了 +100」，不告诉他「因为哪一字段满足了哪一条规则」——这一关的教学价值接近于 0。
- INSPECT 的代价与收益**在感知层不存在**：¥25 对结果零影响（gradeOf 只看 score，资金无门槛），开档瞬间的扣款被反馈遮罩挡住，结算页资金还从 1000 涨到 2125。理性策略是「每单都开档」，张力消失。
- 判定反馈是**结果信号**，不是**可迁移的规则信号**：最大元素是 22px 发光的 CORRECT 印章，依据是 11.5px 的一段话，规则依据是 8px 的裸编号 R01–R05；且遮罩打开时规则抽屉打不开（overlay z=70 > main z=10），最需要查规则的时刻恰好查不到。
- 另有一处同屏自相矛盾：03 号截图顶部标 `UNVERIFIED`、下方面板标 `INSPECTED`（VisitorCard 用 tier 当状态用，与 state.inspected 无关）。

优先级总览：**P0 五项**（首关理解 + 归因闭环 + 状态一致性）、**P1 六项**（可读性地板、动作层级、窄屏）、**P2 五项**（首页/结算/立场页的信息去重）。

## 2. 逐条诊断

### 2.1 第一访客：没有任务，只有界面

02 号截图里，玩家能看到的全部信息是：访客卡、8 行数据、一个 SEALED 面板、一个 `RULES OF THE DAY · 5 ACTIVE` 入口、三个按钮。
缺少的是**一句祈使句**：「判断这个人该不该放行」。

- 唯一的说明在首页（`你是 04 号窗口的审核员…`）和一次性 `TutorialSheet`（6 条纯文字）。关掉模态后，屏幕上不留任何痕迹。
- `RuleToggle` 在滚动区末尾（global.css:519，`margin-top: auto`），390×844 下位于 y≈655，320×568 下在首屏之外。**最主要的参考资料是全场最难到达的元素。**
- 首访客 V-001 是"全绿样本"（signals 为空、eight 行数据完全自洽），正确答案 APPROVE。玩家一路点绿也能过——但不知道自己为什么对。这是最贵的一次教学机会，被浪费了。

### 2.2 字段 ↔ 规则：零显式映射

InfoGrid 的 8 行（ipRegion / timezone / language / accountRegion / service / reason / device / submittedAt）与 RULES 的 7 条（R01–R07）在语义上一一对应，但界面上一根线都没画。
玩家必须同时在工作记忆里持有 8 个值 + 5 条判定条件，才能做出第一次判定——这是本作认知负荷的真正来源，而不是像素字体。
反馈侧同样断链：`JUDGEMENT BASIS` 输出的是 `R01–R05 全部通过：…`，5 个 chip 只有编号没有名称（FeedbackOverlay.tsx:46-51）。

### 2.3 INSPECT：代价看不见，收益不结算

- **代价**：−25 发生在点击瞬间，而状态栏（z=20）被反馈遮罩（z=70）压住；玩家第一次看到这 25 元是在结算页，且被 `+120` 的资金增长掩盖。
- **后果**：`gradeOf` 只读 score，资金全程不参与任何判定；且正确判定 +120，长局下来资金永远是正的（06 截图：¥2125）。
- **收益**：只在信息层，不折成分数，也不在反馈里结算"这条线索是否改变了你的判定"。
- **结果**：不存在 trade-off。全开档 = 250 元 + 10/10，与 3 次开档结果相同。按钮上那个 `¥25` 就成了装饰。
- 次要问题：开档后按钮变灰、副标题变 `FILE OPEN`——玩家无法判断"这次开档有没有用"，也无法判断"什么时候该开"。

### 2.4 状态词汇混乱（同屏自相矛盾）

03 号截图：访客卡右上 `UNVERIFIED`，同一屏 APPLICATION DATA 右上 `INSPECTED`。
根因是 `VisitorCard.tsx:33` 把 `visitor.tier` 当作状态展示，而 `tier: 'inspect'` 是访客**类型**（需开档才能判），与 `state.inspected`（是否已开档）无关；`InfoGrid` 用的是 `inspected`。
再叠加 `FILE SEALED / FILE OPEN`（VisitorCard.tsx:46）、`SEALED / OPEN`（GameScreen 的 DEEP FILE 头）、`SURFACE ONLY`、`INSPECT TO UNSEAL · ¥25`、按钮 `FILE OPEN`——同一件事 9 种说法，其中 2 种互相矛盾。

### 2.5 反馈：给结果，不给归因

- 视觉序列是「印章 → 你选了什么/应该选什么 → 分数变化 → 依据 → 计分表」。学习价值集中在第 4 段，而它的字号（11.5px）和容器（1px 描边灰框）在页面上是最弱的。
- `SCORING TABLE` 每一位访客都完整重放一次（FeedbackOverlay.tsx:55-60），10 次里有 9 次是纯噪声。
- 错误态（无截图，按代码推断）与正确态共用一套结构：没有区分"信息不足（没开档）"、"有线索但看漏"、"规则记错"——三种完全不同的失败，需要三种不同的纠正指令。
- 遮罩打开后规则抽屉不可达（z 序），玩家无法在"我最想确认一下 R02 到底怎么写的"时刻查规则。
- 依赖 22px 印章 + 绿/红发光来表达对错，等于把最强的视觉预算给了**已经知道的信息**。

### 2.6 版面稳定性与窄屏

- `ANOMALY SCAN` 只在有 signals 时插在访客卡与 APPLICATION DATA 之间（GameScreen.tsx:44-59），有无信号时版面跳变；且它给出的描述（`时区与 IP 地区相差 12 小时`）等于直接点名 R02，而 R01–R05 其余条目要玩家自己算——难度曲线不一致，玩家无法建立"机器提示可信到什么程度"的模型。
- 320px：`panel-head` 不换行策略缺失，标题两行、右侧标签掉行，访客卡高度失控，把两行关键字段（DEVICE / SUBMITTED）推出首屏；`.main` 底部没有渐隐或滚动条提示，玩家不知道该继续滑。
- 桌面 1280：手机框居中，两侧全空；对竖屏游戏可接受，但浪费了放"规则/流水"侧栏的机会。

## 3. P0（不做则首关不成立）

### P0-1 局内常驻任务条

**问题**：局内零任务陈述。
**改法**：新增 `TaskBar` 组件（纯展示），插在 `GameScreen` 的 `<main>` 第一个子节点，固定 26–30px 高、不参与滚动。

- 第 1 位访客（`state.index === 0`）显示三步：
  `① 读申请　② 点开 RULES 核对 R01–R05　③ APPROVE 或 DENY`
  同时给 `RuleToggle` 加一次性呼吸高亮（`index===0` 时 `.rule-toggle.pulse`）。
- 第 2 位起收缩为单行：`核对 R01–R05 后判定`，右侧显示 `已开档 ✓ / 未开档`。
- 文案参考：
  - `判断这份申请是否合规：逐项核对规则，然后放行或拒绝。`
  - `规则随时会变，广播出现时先读再判。`

**验收**：5 人中有 5 人能在 20 秒内说出"我要判断该不该放行"；首次判定前打开规则的人数 ≥ 4/5。

### P0-2 字段 ↔ 规则显式绑定

**问题**：8 字段 / 5 规则无连线，工作记忆超载。
**改法**：在 `InfoGrid` 每行右侧加规则码 chip，来源是一张**呈现层**常量（不动 data）：

```ts
// src/components/InfoGrid.tsx 顶部（新增，纯展示映射）
const FIELD_RULE: Record<string, string[]> = {
  'IP REGION': ['R01'],
  TIMEZONE: ['R02'],
  LANGUAGE: ['R04'],
  'ACCOUNT REGION': ['R03'],
  SERVICE: ['R05'],
  REASON: ['R05'],
  DEVICE: ['R06'],
  SUBMITTED: ['R06'],
};
```

- chip 用 `activeRules(index)` 过滤，R06 在第 4 位访客之前不出现，避免提前剧透；R07 不进字段行（它是跨字段的优先级规则，放在规则抽屉）。
- chip 可点：点开 `RuleDrawer` 并滚动/高亮到该条（给 `RuleDrawer` 加 `focusCode?: string`）。
- 行标签改中文主、英文副（`时区 / TIMEZONE`），保证 3 秒内可扫。

**验收**：能在 3 秒内回答"时区不符违反哪条"；错判后能指名"我漏了 R02"。

### P0-3 开档状态只说一种话

**问题**：9 种说法 + 同屏矛盾（03 截图）。
**改法**：

1. `VisitorCard.tsx:33` 的 tier 标签改为**风险类别**，不再借用状态词：
   `STANDARD → 常规`、`ANOMALY/FLAGGED → 需核查`、`INSPECT → 需开档`、`special → 优先处理`、`conflict → 规则冲突`。
   彻底移除 `UNVERIFIED`。
2. 开档状态只在两处表达：DEEP FILE 面板头 + 按钮副标题，词表统一为 `SEALED 未开档` / `OPEN 已开档`。
3. 按钮开档后文案改为 `已开档 ✓`（而不是 `FILE OPEN`），保持禁用态但语义是"已完成"而不是"未知"。
4. `SURFACE ONLY` 改为 `仅表面信息`（中文主），把"还有东西没看"这个暗示说清楚。

**验收**：任意一屏只有一个"是否已开档"的状态词，且不再出现矛盾组合。

### P0-4 INSPECT 的代价与收益必须可结算

**问题**：−25 无后果、无反馈、被遮罩挡住；收益不进结算。
**改法（全部是呈现，不动数值）**：

1. **决策前**：按钮副标题 `¥25 · 余 ¥975`（把绝对值换成"我还能开几次"的预算语义）；第 1 位访客首次 hover/长按给一句 `开档只揭示隐藏线索，不改变判定标准`。
2. **决策中**：`StatusBar` 接收 `flashKey`，点击 INSPECT 时 FUNDS 数字闪一次 amber 并显示 `−25`；同时 DEEP FILE 面板做 300ms 逐行"解密"出现（复用现有 `slide-up`/`steps` 动效语言）。
3. **反馈中**：把 `INSPECT −25` 从灰色 delta 里拆出来，单独一行结算：
   `开档 ¥25 → 2 条线索 → 关键线索 1 条`
   若开档但线索没改变判定，写 `本次开档未提供关键线索（可省）`。
4. **未开档且错判**：明显区分 `你未开档：隐藏线索为「设备指纹命中黑名单 BL-14」，本可看出`。
5. **结算页**：新增 `开档 ROI` 单元格：`3 次 / ¥75 / 改变判定 1 次`，以及 `未开档即错判 N 次`。
6. 遮罩打开时在 sheet 顶部保留一行 `SCORE 400 · FUNDS 1430`（因为原状态栏被压住）。

**验收**：玩家能复述"开档 25、误放行罚 200"；第 2 局"开档次数 vs 正确率"出现正相关（埋点可测）。

### P0-5 反馈重建归因，而不是重播结论

**问题**：结论权重 >> 依据权重；规则查不到；三种失败不区分。
**改法**：

- 结构重排（`FeedbackOverlay.tsx:43-60`）：
  1. 一行小字结论：`判定正确 · 你 APPROVED，应为 APPROVE`（印章从 22px 降到 16px、去掉发光，靠边框与颜色区分）。
  2. **字段对照表**（新，视觉中心）——数据全部现成，不需要改 visitors.ts：

     | 字段 | 申请值 | 规则要求 | |
     |---|---|---|---|
     | 时区 TIMEZONE | UTC−03:00 | NA-04 应为 UTC+09:00（R02） | ✗ |
     | 账号地区 | NA-04 | 需与 IP 一致（R03） | ✓ |

     通过项折叠为一行 `R01 R03 R04 R05 通过`，违规项展开。正确判定的访客则展示"命中项为什么成立"。
  3. 规则 chip 可点，内联展开 `rule.body`（`RulePeek`），不依赖抽屉。
  4. `SCORING TABLE` 只在第 1–2 位访客出现，之后收成一行 `+100 · 误放行 −150 · 误拒绝 −100`。
  5. 三种错误各一句"下次怎么防"：
     - 未开档 → `表面全绿不等于干净：设备指纹与注册时间只在开档后可见（R06）。`
     - 已开档但忽略 → `你已经看到「注册时间晚于提交时间」，这条本身就足以拒绝。`
     - 规则记错 → `R07 优先级高于 R01，冲突时以 R07 为准。`

**验收**：错判后 5 人中 ≥4 人能指出"我漏看/漏开了什么"；不打开规则抽屉也能完成一次归因。

## 5. P2（打磨）

1. **首页**：删掉 `无后端 / 无 API / 可离线`（开发者元信息，2.04:1）；换成钩子 `10 位访客 · 7 条规则 · 中途会变一次`；`BEST SCORE` 提升到可读字号；`justify-content:center` 造成上方约 28% 空白，改 `space-between` 让标题与按钮形成上下两簇。
2. **结算**：`REVIEWED 10/10` 与 `CORRECT 10` 重复，合并为 `审核 10 · 正确 10 · 错误 0`；`误放行/误拒绝` 补英文或统一中文；`FINAL FUNDS` 改称 `预算结余`（现在读起来像盈利）；新增两个区块——`错因回顾`（按规则聚合，数据来自 `records` + `visitor.ruleRefs`）与 `开档 ROI`；`AUDIT LOG` 增加访客姓名列（现在被 `display:none` 藏起来了，ResultScreen.tsx:104）。
3. **立场页**：`STRICT` 红 / `HUMAN` 青本身就是立场暗示，建议两卡同色（中性描边），用图标/排版区分；把 V-010 的两条规则对照折叠展示在卡片上方，让"冲突"可复核。
4. **状态栏**：FUNDS 与 SCORE 同权，但资金无后果 → SCORE 主（15px）、FUNDS 次（11px）；进度 pp 加一次图例（绿=判对、红=判错），否则只是装饰。
5. **桌面端**：≥1024px 时在手机框右侧放常驻"规则 + 审核流水"侧栏，把 1280 的留白变成可用信息。

## 6. 统一文案表（建议采用的唯一词表）

| 概念 | 采用 | 弃用 |
|---|---|---|
| 未开档 | `未开档 SEALED` | SURFACE ONLY / FILE SEALED / INSPECT TO UNSEAL |
| 已开档 | `已开档 OPEN` | FILE OPEN / INSPECTED / UNVERIFIED |
| 隐藏线索 | `隐藏线索` | DEEP FILE（保留为面板名则可，需同一屏只出现一次） |
| 访客类型 | `常规 / 需核查 / 需开档 / 优先处理 / 规则冲突` | UNVERIFIED / FLAGGED |
| 判定 | `放行 APPROVE` / `拒绝 DENY` | GRANT ACCESS / REFUSE ENTRY（可留作副标题，但不必再教一遍） |

## 7. 验证方案（不改规则即可执行）

5 人 · 出声思维 · 第 1 位访客不计时，第 2 位起计时。任务与指标：

1. 打开游戏 20 秒后复述目标 → 目标陈述清晰度（5/5 达标）
2. 第 1 位访客：能否说出"我依据哪条规则放行" → 归因能力（≥4/5）
3. 第 2 位访客：先开档还是先判定？为什么 → INSPECT 决策模型（能说出成本或收益任一即可）
4. 故意判错一次：能否指出漏看项 → 反馈学习信号（≥4/5）
5. 结算页：能否说出"这次哪条规则最常错" → 复盘可读性（≥3/5）

量化埋点（现有 state 已可算，不需改数据）：`inspect 次数 / 首次判定前是否打开规则 / 判错后是否重开规则 / 每规则错误率 / 结算页停留时长`。
